# DES-002 期限日 設計

## 方針
- **DES-001 の構成を維持する。** `todo.js` は純粋関数だけ（DOM・localStorage に触れない）、`app.js` は DOM と保存だけ。外部ライブラリは使わない（NFR-001）。
- **期限日がないときは、DES-001 の振る舞いを一切変えない。** `addTask` と `deserialize` は拡張するが、`dueDate` を渡さない・持たない場合の入出力は従来と同じ。既存のテストは変更せずに通る。
- **日付の文字列化と判定は、すべて `todo.js` の純粋関数に寄せる。** 「今日」も引数で受け取る。`app.js` に判定を置くと自動テストの外に出るので、FR-008・FR-009・NFR-004（期限切れの文字）を自動で確かめられなくなるため。
- 期限日は `YYYY-MM-DD` の文字列で持つ。`<input type="date">` の値と同じ形式なので変換が要らず、ゼロ埋めされた同じ形式の文字列どうしは、文字列の辞書順がそのまま日付順になる。

## 構成
| ファイル | 変更 |
|---|---|
| `site/todo.js` | `isValidDate` `formatLocalDate` `isOverdue` `dueLabel` を追加。`addTask` に `dueDate` を追加。`deserialize` に期限日の正規化を追加 |
| `site/app.js` | 期限日入力の読み取りと、追加後のクリア。行への期限表示。再描画時に「今日」を求めて渡す |
| `site/index.html` | 追加フォームに期限日入力（`#new-due`、ラベルつき） |
| `site/style.css` | 期限日の表示と、期限切れの強調（ライト／ダーク両対応） |
| `tests/` | 下記「テスト計画」のテストを追加（実装時に Codex が書く） |

## データとインターフェース
```
Task = { id: string, title: string, done: boolean, createdAt: number, dueDate?: string }
```
- `dueDate` は省略可。あるときは、実在する日付の `YYYY-MM-DD`。
- 保存先は `todo-lab:v1` のまま、キーのバージョンは上げない。`dueDate` は読む側が省略を許すフィールドの追加なので、旧データがそのまま読める（FR-010）。
- 期限日がないタスクは、`dueDate: undefined` ではなく、**プロパティ自体を持たない**。

| 関数（`todo.js`） | 振る舞い |
|---|---|
| `isValidDate(value)` | `YYYY-MM-DD` の形式の文字列で、かつ実在する日付なら true。`2026-02-30`、`2025-02-29`、文字列でない値は false。`2024-02-29` は true。形式の検査のあと、年月日に分解して `Date.UTC` で組み立て直し、元の年月日と一致するかで実在を確かめる |
| `formatLocalDate(date)` | `Date` を**端末のローカル日付**の `YYYY-MM-DD`（ゼロ埋め）にする。`getFullYear` `getMonth` `getDate` を使う。`toISOString` は UTC なので使わない（日本では 0〜9 時台に前日になる） |
| `isOverdue(task, today)` | `today`（`YYYY-MM-DD`）より前の `dueDate` を持ち、かつ `done` でなければ true。期限日なし・当日・未来・完了済みは false。値の検証はしない（保存と追加の時点で `isValidDate` を通っている前提） |
| `dueLabel(task, today)` | 期限日がなければ `null`。あれば `{ text, overdue }`。`text` は期限切れでなければ `期限 2026-11-05`、期限切れなら `期限切れ 2026-11-05` |
| `addTask(tasks, rawTitle, {id, now, dueDate})` | **変更点**: `dueDate` は省略可。`isValidDate` を通れば、そのタスクに `dueDate` を持たせる。空文字・undefined・不正な値は無視し、期限日なしで追加する。タイトルが空のときに同じ配列を返す振る舞いは変えない |
| `deserialize(json)` | **変更点**: Task の形に合う要素のうち、`dueDate` が不正（形式違い・実在しない日付・文字列でない）なものは、**タスクを残して `dueDate` だけを取り除く**。保存データの一部が壊れても、タスクを失わないため |

`filterTasks` `toggleTask` `removeTask` `countActive` `serialize` `normalizeTitle` は変更しない。

## 画面・振る舞い
- 追加フォームに「期限日（任意）」の `<input type="date">` を置く。`<label for="new-due">` を付ける（NFR-002 を維持）。タイトル入力・期限日入力・追加ボタンのどこで Enter を押しても、ネイティブの動作で送信される。
- 追加に成功したら、タイトル入力と期限日入力の**両方を空に戻す**（期限日を次のタスクに引き継がない）。タイトルが空で追加されなかったときは、期限日入力はそのまま残す。
- 一覧の各行に、`dueLabel` の `text` を表示する。`null` なら何も出さない。`text` は `textContent` で入れる（DES-001 の方針を維持）。
- `overdue` が true の行には `overdue` クラスを付ける。強調は**色と文字の両方**で行う。文字は `dueLabel` が出す「期限切れ」で、色は枠線と期限表示の文字色（NFR-004）。
- 完了にすると、期限日の表示は残り、「期限切れ」の文字と強調だけが外れる（FR-009）。未完了に戻すと再び付く。
- 「今日」は、再描画のたびに `formatLocalDate(new Date())` で求めて `dueLabel` に渡す。日付をまたいでも自動では更新されず、次の再描画（操作）で変わる。
- 再描画後のフォーカス復帰は DES-001 のとおり（切り替え → 同じ行のチェックボックス、追加・削除 → 入力欄）。
- 色は、ライト・ダークそれぞれで、背景に対して 4.5:1 以上のコントラストを確保する。実装時に値を確認する。

## 設計判断（要件に書かれていないこと）
- 期限日の表示形式は `YYYY-MM-DD` のまま。曖昧さがなく、実装が単純。
- 過去の日付も入力できる。入力時の警告・拒否はしない（その日付のタスクは、追加した時点で期限切れとして表示される）。
- 期限日のないタスクには、期限に関する表示を一切出さない。
- 一覧の並び順は、DES-001 のとおり追加順。期限日では並べ替えない。
- 不正な `dueDate` は、`addTask` では無視（期限日なしで追加）、`deserialize` では取り除く（タスクは残す）。どちらも、タスクを失わない側に倒している。
- 保存キーのバージョンは上げない。

- `[FR-007]` 空文字・undefined・`2026-02-30`・`2026/11/05`・数値などの不正な `dueDate` は無視され、期限日なしで追加される。
- `[FR-007]` `isValidDate` が、実在しない日付（`2026-02-30`、`2025-02-29`）を弾き、閏日（`2024-02-29`）を通す。

### 手動（`npm run serve` で確認）
- **M-1** 期限日を指定して追加すると、行に `期限 YYYY-MM-DD` が出る。指定しなければ何も出ない。追加後、期限日入力が空に戻る。
- **M-2** 昨日の日付で追加すると「期限切れ」と強調表示される。今日の日付・明日の日付では強調されない。
- **M-3** 期限切れのタスクを完了にすると強調が消え、未完了に戻すと再び付く。
- **M-4** DevTools で `localStorage.setItem('todo-lab:v1', JSON.stringify([{id:'a',title:'旧',done:false,createdAt:1}]))` を実行して再読み込みすると、タスクが表示され、期限に関する表示は出ない。
- **M-5** キーボードだけで、タイトル入力 → 期限日 → 追加が操作できる。色を無視しても（またはスクリーンリーダーで）、期限切れが文字で分かる。

## リスクと未決事項
- **REQ-002 は Claude の下書き（draft）。** 承認前に要件が変われば、本書も変わる。
- 日付をまたいでも、次の再描画まで「期限切れ」の表示は更新されない（タイマーは使わない）。
- 日付入力に対応していない古いブラウザで、入力欄が文字入力になった場合、不正な値は黙って無視される（期限日なしで追加される）。必要なら、入力時のエラー表示を設計し直す。
- `isOverdue` は値を検証しない。呼び出す側（保存・追加）で `isValidDate` を通す前提。
- 追加後に期限日を変更できない（REQ-002 のスコープ外）。時刻を扱う拡張をするときは、保存形式のバージョン（`v2`）が必要になる。
